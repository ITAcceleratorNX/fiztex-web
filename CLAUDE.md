# fiztex-web

Desktop-админка Fiztex. Vite 5 + React 18 + TypeScript, Tailwind CSS 3.4,
react-router 6, TanStack Query 5, lucide-react. Тесты — Vitest + Testing Library.

```bash
pnpm dev          # vite dev server
pnpm build        # tsc -b && vite build
pnpm lint         # tsc -p tsconfig.app.json --noEmit
pnpm test         # vitest run
```

## Типы API

`src/lib/api-types.ts` **сгенерирован** из `fiztex-back/docs/openapi.json`
(`pnpm gen:api`) — не править руками, изменения затрутся.

```ts
import type { Schema } from '@/lib/apiSchemas';
type Year = Schema<'AcademicYearView'>;
```

Новые DTO брать оттуда, а не дописывать в `src/lib/types.ts`. `types.ts` —
ручной legacy Scope 1; он остаётся рабочим, но не растёт. Искать эндпоинт —
грепом по `fiztex-back/docs/api-map.md`, а не чтением Java-контроллеров.

Сгенерированные поля ответов помечены `?` (springdoc не знает nullability
Java-полей). Это не значит, что поле может не прийти.

## Дизайн-токены

CSS-переменные объявлены в `:root` в `src/index.css`, в утилиты проброшены
через `theme.extend` в `tailwind.config.js`. Доступны `text-10`, `text-11`,
`text-13`, `text-15`, `text-28`, `shadow-popover`, `text-ink`, `text-muted`,
`border-line`, `bg-surface`, `bg-disabled`, `bg-info-bg`, `bg-success-bg`,
`text-success-fg`.

Не хардкодить hex и не писать `text-[13px]` — брать токен. Нет токена —
сначала завести его в `:root`.

Ограничение: цвета-токены объявлены как hex, поэтому модификаторы
прозрачности (`bg-info-bg/50`) на них не работают. Понадобится — заменить
значение на RGB-каналы и обернуть в `rgb(var(--…) / <alpha-value>)`.

### Откуда взяты значения

Источник — Figma `Copy of fiztex`, страница «Admin schedule » (node `2015:4887`,
59 экранов). **В файле объявлены только две переменные** — `brandcolor`

## Посещаемость урока

Лист урока — `/lesson-schedule/lessons/:lessonId/attendance`
(`platform/pages/schedule/LessonAttendancePage.tsx`), вход с плитки на карточке
урока. Просмотр и правка — режимы одного экрана, как в макете.

Правила отметки (какие сочетания `status`/`mark`/`reason` допустимы, что чистится
при смене статуса, что уходит в `PATCH`) живут в `src/lib/attendanceModel.ts` и
только там: то же правило продублировано в мобилке, и разъехаться им нельзя —
цифры месячных сводок считает бэкенд. Что разрешено делать, экран не вычисляет:
`canFill`/`canPublish`/`reminder` приходят посчитанными.

Сгенерированные типы знают только `undefined` (springdoc не описывает nullability),
а бэкенд шлёт `null`. Поэтому очистка поля — это `undefined` (ключ исчезает при
сериализации, Jackson читает его как `null`), а чтение — терпимое (`?? null`).

Даты одного занятия переключает `LessonDatePicker`: `LessonView.scheduleLessonId` —
ссылка на слот расписания, по ней `GET /api/lessons?scheduleLessonId=` отдаёт то же
занятие в другие дни. Отбор идёт по физическому слоту (класс, подгруппа, день недели,
время), а не по строке таблицы, поэтому переживает переиздание расписания.

Контракт экрана — `.cursor/tasks/attendance/screens/LessonAttendancePage.md`,
контракт API — `fiztex-back/docs/attendance-read-contract.md`.

### QR-отметка

Кнопка «Показать QR» и полноэкранный код (`AttendanceQrOverlay`) живут на том же экране;
код рисует `QrPoster` (`qrcode.react`). **Оверлей и есть сессия:** открыть — `POST …/qr`,
закрыть — `POST …/qr/close`, и все выходы (`Esc`, крестик, «Закрыть») делают одно и то же.
Уход со страницы код не гасит — сервер перестанет его принимать в конце урока.

Источник отметки в самом листе бэкенд **не отдаёт**: чипы «QR» в строках берутся из
`scans[]` того же `GET …/qr`. Отсюда правило: если экрану нужно знать, кто отсканировал,
он спрашивает QR-эндпоинт, а не ищет поле в листе.

Скан ученика **не двигает версию листа** (`fiztex-back/docs/attendance-qr-contract.md` §6),
поэтому поймать устаревание по `version` нельзя — экран с открытым кодом перезапрашивает
состояние сам.

Счётчика отметившихся и таймера нет намеренно: ТЗ FE-001 §7 исключает оба, хотя
`scannedCount` приходит тем же ответом. Дизайн-решения — `.cursor/tasks/attendance-qr-fe/01-ux.md`.

## Оценки и журнал

Три экрана одного модуля, и граница между ними важна:

| Экран | Путь | Что делает |
|---|---|---|
| Оценки урока | `/lesson-schedule/lessons/:id/grades` | единственное место, где оценку ставят |
| Журнал | `/grades` | зеркало: показывает и ведёт в урок, ничего не пишет |
| Итоги четверти | `/grades?tab=finals` | единственное место, где живёт итоговая |

**Права не вычисляются на фронте.** Лист урока приходит с посчитанными
`canManageGrades`, `writeState` и `canEdit` у каждой оценки, экран итогов — с `canManage`
(`docs/grades-read-contract.md` §3.1, `docs/final-grades-contract.md` §5). Правила окна
замещающего, отменённого урока и «админ оценок не ставит» живут на бэкенде; повторить их
здесь — значит получить активную кнопку и отказ в ответ на неё.

**Ничего не считается на фронте.** Средние и рекомендации приходят готовыми: у журнала,
дневника ученика и рекомендации итоговой обязана быть одна арифметика.

**Шкала — справочник** (`GET /api/grades/scale`), а не константа клиента; в запросах
значение — код (`4+`), а не число. Типы оценки берём из `gradesModel.ts`: в Figma список
свой («Диктант», «Реферат»), в API его нет — приоритет за backend-ТЗ.

Компоненты: `ui/GradeChip` (клетка) и `ui/GradePicker` (выбор значения и типа) — общие для
урока и журнала. Логика окна «месяц» и подписей колонок — `lib/journalModel.ts`.

## Рабочее время учителя

Занятость правит админ (`/lesson-schedule/teachers`), а учитель её **просит**:
`/my-availability` отправляет заявку, и часы меняются только после утверждения.
Причина не в правах, а в расписании — занятость читает движок конфликтов, и учитель,
молча снявший с себя день, оставил бы уроки опубликованного расписания без преподавателя.

Заявка живёт своей таблицей (`teacher_availability_proposals`), а не `PROPOSED`-строками
в `teacher_working_time`: она меняет ещё и `working_days`, которых в строке интервала нет,
а всё, что читает `ACTIVE` working-time, продолжает видеть только утверждённые данные.
До решения админа заявку не видят ни движок конфликтов, ни сводки занятости.

**Утверждение не пишет в занятость отдельно** — оно вызывает тот же
`saveAvailability`, что и админский `PUT`. Отсюда и одна валидация (В1–В5 проверяются
дважды: при отправке и при утверждении), и `approvedBy` = утвердивший админ.

Заявка на рассмотрении приходит полем `TeacherAvailabilityView.pendingProposal` — тем же
ответом, что и занятость: второй запрос дал бы админу две версии одного состояния.
В сводке она — отдельный `pendingProposal: boolean`, а не третье значение `availability`:
строка обязана говорить обе вещи сразу, «часы согласованы» и «учитель просит их изменить».

Контролы обоих экранов общие (`availabilityControls.tsx`) — учитель просит те же часы,
которые админ утверждает, и разъехавшиеся формы означали бы, что заявка описывает не то,
что видит утверждающий. **Сетки уроков на учительском экране нет:** её строки — периоды
шаблона звонков, а шаблоны лежат под `/api/admin/*`, куда учительскому токену нельзя.
Вместо неё список интервалов с удалением (`IntervalListEditor`).

Контракт — `fiztex-back/docs/schedule-constructor-read-contract.md` §10.

## Сервисные заявки

Один экран (`/service`) на две роли, вкладка живёт в адресе (`?tab=all`). Admin и
Teacher видят «Мои заявки» и «Историю», Super Admin — их же плюс «Все заявки» и
«Журнал». Общей очереди нет ни у кого: это исполнительский раздел мобилки.

Границу «своё / всё» держат два разных клиента: `serviceRequestsApi.ts` — сценарий
автора (создать, отменить новую, вернуть выполненную), `serviceRequestsAdminApi.ts` —
чтение всей школы и глобальный журнал. Второй состоит из одних `GET`, и это не
самоограничение экрана: эндпоинтов, меняющих чужую заявку, на бэкенде нет вовсе
(`ServiceRequestAdminController`). Отсюда же read-only чужой карточки — `canCancel` и
`canReturnCompleted` спрашивают, автор ли смотрящий, и Super Admin просто не проходит
проверку.

Порядок «последняя активность сверху» — это `updatedAt DESC` на сервере; пришедшую
страницу не пересортировывают. Все семь фильтров (§6) и общий поиск (§7) тоже уходят
параметрами: отбирать двадцать строк на клиенте значит фильтровать внутри чужого среза.

Карточка возвращает туда, откуда её открыли: источник передаётся в адресе
(`/service/12?from=audit`), а не состоянием истории — ссылку на заявку пересылают.

Контракты: `fiztex-back/docs/api-map.md` → `/api/admin/service-requests`, ТЗ
SERVICE-BE-002…007 и SERVICE-FE-001/004.

## Внутренние сотрудники

`/admin/employees` — раздел Super Admin внутри «Пользователей»: клининг, техслужба,
охрана. Отдельной страницей, потому что ролей три, а `/admin/accounts` принимает одну
за раз (`listAccountsByRoles` разворачивает набор в параллельные запросы).

**«Заблокировать» — это `block`.** Возврат заявок в очередь живёт там же: `block`
публикует `AccountDeactivatedEvent`, а `ServiceRequestAssignmentReleaseListener` снимает
с сотрудника его `IN_PROGRESS` (SERVICE-BE-007 §9). Экран этого не повторяет и не
досчитывает — перечитывает списки по ответу.

Слова те же, что в общей таблице «Пользователи»: ТЗ §3 называет состояния Active /
Inactive, но действие за ними одно и то же, и звать его двумя словами в двух разделах
одной панели значило бы делать вид, что это разные операции. Active / Inactive остались
только крупными мазками фильтра; в строке стоит настоящий статус аккаунта.

**Занятый телефон проверяется до создания**, а не по 409: бэкенд отвечает голым
`FiztexConflictException("Phone is already in use")` без кода, и сценарий реактивации,
привязанный к тексту сообщения, сломался бы от правки формулировки. Найденный неактивный
аккаунт возвращается в строй `unblock`, дубль не заводится.

Правила ролей и статусов — `src/lib/employeesModel.ts`. `NOT_ACTIVATED` там считается
активным: аккаунт никто не выключал, человек просто ещё не входил.

**Смена роли и сброс доступа** — `PATCH /api/admin/accounts/{id}/role` и
`POST /api/admin/accounts/{id}/reset-access` (SERVICE-BE-008). Первая возвращает в очередь
только те заявки сотрудника, что новая роль больше не обслуживает, — решает это бэкенд,
экран лишь перечитывает списки. Вторая гасит текущую сессию и выдаёт код активации: он
показывается один раз, поэтому живёт в отдельном окне, а не в тосте.

Роль меняется только между тремя служебными; перевод учителя в клинеры бэкенд отклоняет
409 — у него школьная карточка, классы и назначения.

Раздел спрятан от обычного Admin через `isRouteAllowedForRole` — это продуктовое
решение ТЗ §3, а не защита: бэкенд `ACCOUNT_CREATE`/`ACCOUNT_BLOCK` даёт и ему.

### Формулы

Текст вопроса, варианта ответа, эталонного ответа и критериев может содержать формулы
(`$…$`, `$$…$$` — см. `fiztex-back/docs/formula-contract.md`). Выводить такой текст только
через `MathText`, а не `{q.text}`: иначе ученик увидит разметку. Редактирование —
`FormulaField` (поле + кнопка «Формула» + предпросмотр), окно формулы — `FormulaEditorModal`
(MathLive подгружается динамическим `import()`). Живая проверка полей — `lib/formulaChecks.ts`.

### Рисунок к вопросу

Схема, график или чертёж хранится не в теле теста, а своим эндпоинтом
(`POST/DELETE /api/admin/questions/{id}/image`), поэтому сохранение вопросов его не трогает.
Загрузка — `QuestionImageField` (только для уже сохранённого вопроса: у нового нет id), показ
ученику и в разборе — `QuestionFigure`. Увеличение — наложение внутри страницы, а не новая
вкладка: во время попытки уход со страницы античит считает нарушением.

### Как читать макет

`get_variable_defs` требует **слой**, а не страницу: на node страницы
(`2015:4887`) он падает с невнятным «nothing selected». Передавайте id фрейма.
